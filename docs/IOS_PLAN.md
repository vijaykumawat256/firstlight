# Firstlight for phones: iPhone, iPad and Android

*Started 22 November 2026, at the user's request ("yes please make for ios"). This changes an earlier decision: CLAUDE.md
and docs/PHASE7_DESIGN.md said a phone version would be the web build and that nothing native for phones was planned.
The iPhone app is the same Tauri app built for iOS, so it shares almost all of its code with the desktop.*

## What it is

The same app on the phone: your briefing, calendars, tasks and notes, with the same encrypted database on the phone and
the same "nothing leaves the device except to services you connect" rule. It keeps in step with your computers through
the sharing that already exists (a Google Drive or OneDrive app folder, or the same network), using the same sync code.

A phone has no unlock event an app can hear, no menu bar, no system-wide shortcuts and no floating windows, so the phone
app is something you open, plus notifications (and later a widget). "Appears when you unlock" stays a computer feature.

## Things that work differently on iOS

- **Sign-in.** The desktop app receives the Google/Microsoft answer on a small local web server. iOS suspends an app
  that is in the background, so that doesn't work while the browser is in front. The iOS way is
  `ASWebAuthenticationSession` returning to a custom URL scheme (Google: an iOS client ID with its reversed-client-ID
  scheme; Microsoft: a `msauth.<bundle id>://auth` redirect on the same app registration). Needs new registrations by
  the user, and a small native plugin (Swift) for the session.
- **Same-network sharing.** Since iOS 14, sending UDP broadcasts needs Apple's multicast networking entitlement
  (`com.apple.developer.networking.multicast`), which Apple grants on request. Two options: ask Apple for it (the
  current protocol then works unchanged), or have phones find computers with Bonjour (`_firstlight._tcp`), which needs
  no entitlement, only `NSBonjourServices` in Info.plist. Bonjour is the better long-term answer; the TCP exchange and
  the sealing stay as they are. Either way the phone only shares while the app is open.
- **Background.** No always-running threads: the scheduler, notifier and network threads stop when iOS suspends the
  app. Calendar refresh runs when the app opens and in system-scheduled background refreshes; reminders and heads-ups
  must be handed to the system as scheduled notifications in advance.
- **Not on iOS at all:** Outlook (Windows), Apple Mail through AppleScript (no AppleScript on iOS), Do Not Disturb
  shortcuts, the Apple Maps travel check as written (MapKit exists on iOS, so it could come back), files in Downloads
  (exports and problem reports need the share sheet instead).

## What the user needs to provide

- An Apple Developer account ($99 a year) for running on a real phone longer than 7 days, TestFlight and the App Store.
  Without one, Xcode can put the app on your own phone with a free account for 7 days at a time.
- For sign-in: an iOS OAuth client in Google Cloud, and the iOS redirect added to the Microsoft app registration.

## How to run it

- Simulator: `npx tauri ios dev "iPhone 18 Pro"` (needs Xcode, the iOS simulator runtime, `brew install xcodegen`,
  `rustup target add aarch64-apple-ios aarch64-apple-ios-sim`).
- Your own phone (done 22 Nov 2026 on an iPhone 15 with a free Personal Team): connect it, then
  `APPLE_DEVELOPMENT_TEAM=<your team id> npx tauri ios build --export-method debugging` and
  `xcrun devicectl device install app --device <udid> src-tauri/gen/apple/build/arm64/Firstlight.ipa`
  (`xcrun devicectl list devices` shows the udid). Keep the team id out of the committed project file. With a free
  team the app stops opening after 7 days; build and install again. Or: connect it, open `src-tauri/gen/apple/firstlight.xcodeproj` in Xcode, choose your team under
  Signing & Capabilities, and run.

## Android (Google, Samsung and other phones)

- Same app, `src-tauri/gen/android` (kept in git), `tauri.android.conf.json` (same identifier, Android 8+). Build with
  `scripts/android-env.sh npx tauri android build --apk --target aarch64` (the script sets the NDK tools the bundled
  OpenSSL needs). `scripts/mobile-check.sh` type-checks both phones.
- Secrets: the `keyring` crate has no Android backend and silently kept secrets in memory (the database key would be
  lost at each restart). `src-tauri/src/android_secrets.rs` + `SecretsPlugin.kt` keep them AES-GCM sealed under a key in
  the Android Keystore. Verified on an emulator: the database opened again after the app was stopped and restarted.
- Certificates: Android's own checker is only reachable from Java, so `firstlight_core::tls` uses the bundled Mozilla
  list there (`webpki-roots`); everywhere else the system checks them as before.
- No Google backup or device-to-device copy of the app's data (`allowBackup=false`, `data_extraction_rules.xml`).
- Ran on a Pixel 6 emulator (Android 15): welcome screen, encrypted database, backup. Not yet on a real phone.
